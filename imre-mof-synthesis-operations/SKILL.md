# IMRE MOF Synthesis Operations

## Overview

Operate the IMRE MOF synthesis cell as one coordinated physical system. This
skill combines PUDA control-plane checks, machine-specific safety gates,
calibrated motion and liquid-handling procedures, camera evidence, recovery
boundaries, and UUID-linked provenance for synthesis workflows.

## Use when

- Running or authoring MOF synthesis workflows across the IMRE automation cell.
- Moving labware with the Dobot, pipetting with PipQuBot MOF, or operating the BioShake, centrifuge, capper, or plate reader.
- Restarting/rebuilding an IMRE edge, clearing faults, reconciling an interrupted run, or diagnosing a stuck protocol.
- Calibrating labware positions, validating camera-guided motion, or reporting whether a requested physical action completed.

Use alongside the project-specific machine reference and the `puda-protocol` skill. For physical tray open/close requests on PUDA-connected plate readers and similar instruments, follow [references/plate-reader-tray-operations.md](references/plate-reader-tray-operations.md) for live command discovery, unobstructed-path preflight, one-command execution, independent tray-state verification, and limits on what tray telemetry proves. For plate-reader spectra when the edge exposes only one-wavelength reads, follow [references/plate-reader-spectral-scans.md](references/plate-reader-spectral-scans.md) for explicit interval selection, deterministic protocol expansion, interrupted-run suffix recovery, complete JSON-response parsing, artifact provenance, and raw-versus-blank-corrected reporting. For long multi-reagent liquid-transfer runs, also follow [references/long-run-liquid-transfer-monitoring.md](references/long-run-liquid-transfer-monitoring.md) for layered live preflight, NATS consumer checks, passive per-ejection camera evidence, durable background execution, and post-run reconciliation. For centrifuge close/spin/wait/open cycles—especially when a late websocket error conflicts with completed physical lid motion—follow [references/centrifuge-lid-command-reconciliation.md](references/centrifuge-lid-command-reconciliation.md) for robot-clearance gating, telemetry/camera reconciliation, stop-event timing, and honest audit language.

## Core safety model

Treat these as separate facts and report them separately:

1. **Edge health** — container/process and NATS connectivity.
2. **PUDA run state** — `idle`, `active`, or `busy`.
3. **Controller session health** — whether the edge's existing controller session can execute commands.
4. **Physical outcome** — verified robot pose, gripper/labware state, and final location.

A healthy container, NATS connection, or `idle` state does **not** alone prove controller readiness, pose, or physical completion.

## Standard movement procedure

1. Load the machine reference and run `puda machine list`, then copy the exact registered ID into `puda machine commands <machine-id>`; use only exposed commands and documented poses. Do not shorten or alias the ID (for example, `m1pro` versus registered `dobot-m1pro`). A wrong-but-plausible ID can surface as `KV bucket not found` rather than a clear “unknown machine” error; treat that first as an identifier mismatch and retry with the exact discovery result, not as evidence that the live edge or NATS KV is broken.
2. Check `puda machine state <machine-id>` and edge/container health before issuing a motion. Require both `state=idle` **and** `run_id=null`: an idle state with a non-null retained run can still reject the next `START` as “currently running,” even when both machine consumers have zero pending and zero ack-pending work. Queue emptiness proves there is no queued command; it does not clear run ownership. When this stale-run signature appears, inspect the last command response and logs to establish the physical completion boundary, then use `puda machine reset <machine-id>` only when `reset` is exposed. Recheck `idle`, `run_id=null`, empty queues, and controller readiness before retrying the blocked operation. Remember that reset may also invoke the device driver’s controller reset; do not treat it as bookkeeping-only or use it when the prior command’s physical outcome is uncertain.

   For enclosed robots with a camera, capture a fresh pre-motion frame and treat any visible person, head, hand, or body part inside the enclosure as a hard stop. Do not dispatch the command; verify the machine remains idle. After the area is cleared, capture and inspect a new frame rather than relying on the earlier image.
3. Prefer a first-class PUDA operation when it exactly matches the request—for example, use `puda machine home <machine-id>` for an explicit home request instead of creating a one-step protocol. Treat an operator label such as “Home target” as descriptive rather than authoritative: compare every supplied coordinate against the machine’s configured/native home pose. If any axis differs (for example, native `R=20` versus requested `R=22`, or a non-home Z), execute and independently verify the exact supplied Cartesian target with the safe motion primitive; do not substitute native home or claim that a native-home run satisfies the custom target. Before homing, account for installation-specific side effects and the full swept path: this M1 Pro's home operation opens the gripper and rotates to its configured home R, so verify that nothing is intentionally held and that wrist-camera cable slack covers the entire current-R-to-home-R sweep. Also inspect the deployed home/reset implementations before recovery: this driver selects the initial safe-height lift using the branch already active when `home()` starts, while `reset` performs `ClearError → DisableRobot → EnableRobot` and can permit a loaded arm to settle or swing. Never set the destination/home branch while still at an incompatible low pose; restore the source-compatible branch, lift and verify at safe Z, then select the home branch. After any reset, discard the pre-reset pose and immediately remeasure/reimage. If a safe-Z home attempt moves partway and then reports `RobotMode 9` or error `-2`, stop rather than automatically resetting or trying the opposite branch; follow [references/dobot-m1pro-verified-motion.md](references/dobot-m1pro-verified-motion.md). Require onsite inspection and controller/pendant recovery before any new motion. Even after that clearance, treat an opposite-branch home as a distinct monitored recovery attempt: if `MovJ(home)` is accepted but `Sync()` times out or the move-port disconnects, immediately run only a read-only pose check. If the pose is unchanged, classify it as accepted-command/no-motion failure, do not reset or resend home, and request the exact pendant mode/alarm/safety-stop indication. If prior visual-servo work accumulated substantial physical rotation, do not let the native home command choose a short numeric R path that adds more wrap. First unwind in the reverse *physical* direction using bounded R-only waypoints at fixed fresh X/Y/Z, preserving direction across the ±180 representation boundary (for example, negative physical rotation can use `-152 → -175 → +175 → +120 → +60 → +20`), with fresh overhead cable checks between major legs; then invoke native home once R already equals the configured home orientation. Verify robot home pose and wrist-camera health as separate outcomes; exact controller-confirmed home can succeed even if the USB camera disconnects during the motion. If the home response and edge log show the final `MovJ` accepted and `Sync()` succeeded but the immediate independent `get_pose` times out, preserve that distinction: home has strong controller-completion evidence, while independent pose verification is unavailable. Before restarting the edge for the timed-out read, check noncompeting network reachability (route/ICMP) and queue emptiness; when the controller IP is unreachable, do not restart merely to repair the read because restart cannot restore network/power reachability and may remove the edge from live registration. Report the completed home evidence and the verification/controller-connectivity degradation separately.
4. For named stations such as A1 or CAP, resolve the coordinates from existing project protocols and `project.md`. Distinguish a safe approach pose from the lower pickup/place/process pose; never infer a process depth from the station name alone. For pipetting requests that name a well such as `E5`, inspect the live `attach_tip` signature: pass slot/well identifiers only when those parameters are exposed; if the deployed edge requires raw `x`, `y`, and `z`, obtain the authoritative active-deck calibration and do not synthesize coordinates from the well label. Treat reference machine IDs as examples until `puda machine list` confirms the currently registered edge ID. When a named-pose label matches multiple UUID calibration files (for example a retained superseded and the current `centrifuge_2_center`), resolve to the active record by following the `supersedes_calibration_id` chain and `calibration_recorded_at`; never choose by filename or directory order. The older file is preserved provenance, not a motion target — confirm the resolved pose's `machine_id` and `coordinate_frame` match the request before executing. After any approved labware-table revision, re-read the active artifact before the next named-well move and author a fresh motion protocol from that value; do not reuse an older protocol merely because its well label matches, because PUDA protocols embed coordinates rather than live aliases.

   When an operator follows a named-well move with small explicit Cartesian adjustments, treat each numeric request as a **one-shot position probe**, not an automatic calibration edit. Use one motion-only command with no gripper actuation, preserve the exact requested axes, independently read back the endpoint, and report the actual path semantics (the deployed M1Pro `safe_move` may rise to safe Z even for a sub-millimetre X/Y adjustment). For successive low-Z probes at distinct X/Y values, do not carry forward the prior endpoint's clearance confirmation merely because the adjustment is small: stage at the new X/Y/R at inspection height, verify and inspect, then obtain exact-endpoint operator confirmation whenever local clearance remains occluded or the wrist camera is unavailable. Keep the stage and final descent as separate protocols/runs so the inspection and approval boundary remains enforceable. A return to a previously cleared low-Z endpoint may reuse that clearance only when the complete `[X,Y,Z,R]` is identical, all intervening motion was logged and independently verified, no manual access/restart/fixture change or ambiguous run occurred, and a fresh broad frame shows no change; otherwise repeat the stage-and-confirm cycle. Follow [references/dobot-m1pro-motion-only-position-probes.md](references/dobot-m1pro-motion-only-position-probes.md). Do not overwrite the UUID-backed labware artifact or relabel the tuned endpoint as the new well coordinate until the operator explicitly approves it as a calibration. If such a probe interrupts a larger transfer workflow, leave the unexecuted suffix stopped; never resume it automatically after the probe.
5. Reuse an existing validated movement protocol when possible. If none exists, create one clear operation, validate it, and record creation according to the `puda-protocol` and `puda-memory` skills.
6. Record run outcomes in `project.md` and retain the command output in a run log. Treat `project.md` as a shared concurrent-write surface: immediately before editing, re-read the exact `## Protocols` or `## History` neighborhood; never patch from an old partial read. If the patch tool reports that another writer changed the file, re-read and reconcile only the affected lines—preserve every concurrent entry rather than restoring an older block wholesale. Avoid broad fuzzy replacements around headings because they can silently displace the newest adjacent entry. After insertion, perform count-based verification with the new protocol/calibration/run IDs, remove only proven duplicates, and confirm any concurrent IDs observed during reconciliation remain present. A successful patch response alone is not proof that the shared record is correct. Invoke file-backed protocols with the explicit flag, `puda protocol run -f <protocol.json>`; do not pass the path positionally. When piping that command through `tee`, always enable `set -o pipefail` (prefer `set -e -o pipefail`) and inspect the protocol body: without pipefail, a failed PUDA command can be masked by `tee` and the shell may misleadingly exit `0`. Conversely, do **not** append an early-closing consumer such as `head` to the live `tee` pipeline under `pipefail`: it can terminate upstream with SIGPIPE and produce exit `141` after a physically successful protocol. Persist the complete output first, capture the PUDA command's own exit status, and parse the saved log in a separate step (or use a filter that consumes the full stream). Treat exit `141` as an evidence-reconciliation trigger, not automatic motion failure.
7. Confirm completion from the command/protocol response plus edge logs. For blocking movements, require a post-`Sync` measured pose within an explicit tolerance and run a second edge-mediated pose query as an independent check when exposed (`get_pose` for Cartesian robots, `get_position` for gantries). Treat any pose merely echoed by the motion command as a commanded target, not proof of movement. Report the independently measured pose, final machine state, and run ID.
8. When changing robot speed, trace the full motion call chain rather than editing one parameter in isolation. Distinguish safe-path lift/lateral/descent factors from any extra movement issued by `pick_from` or `place_to`. If the operator wants those commands to inherit `safe_move`, remove duplicate same-target moves and their explicit overrides instead of merely deleting a speed argument. Add regressions for both per-segment factors and the absence of post-`safe_move` movement, redeploy the edge, and inspect the live container methods—not just the checkout—to verify the running behavior. See [references/dobot-capper-loop-workflows.md](references/dobot-capper-loop-workflows.md).
9. For Dobot M1 Pro wrist-camera alignment that must hold X/Y/Z fixed and vary only R, use a bounded image-feedback probe rather than assuming rotation direction. In a sequential request for the cap “on the left,” define “left” from the **newest frame and currently centered cap**, then lock that newly adjacent cap; do not keep steering the previously centered component. Treat prior adjacent-cap `ΔR` only as a seed, recompute local pixel-per-degree sensitivity from nearby fully visible frames, and correct a small overshoot with a bounded reverse sub-degree step. If the operator identifies an adjacent target in an annotated upload, use the annotation only to establish target identity, then track that same target in fresh unannotated live frames; annotation pixels and clipped-edge centroids can corrupt segmentation and must not drive a final extrapolation. For non-orange targets such as a dark empty slot, identify and measure that feature directly from its relation to neighboring objects rather than steering from orange segmentation. Distinguish a physical printed marker from an annotation arrow **and from other arrow-like rotor symbols**. Before motion, write down a positive target signature from the operator’s crop (for example, “solid white shield/chevron containing a black downward arrow”) plus explicit negatives (“not the thin outlined triangular warning symbol; not the nearby cap”), then match that signature in a fresh live frame. If multiple plausible symbols remain, ask or use the replied-to crop to disambiguate before steering; visual similarity is not enough. If the operator corrects target identity after motion, mark the previous alignment invalid, restart localization from a fresh frame, and do not reuse its centroid or optimum R. Treat a supplied R interval as a cable-safety bound rather than a requirement to sweep the full range; when the correct physical marker is already visible, use local probes and stop at the first verified optimum. If the correct marker is absent, search in bounded monotonic R steps with fresh target and cable checks after every step, preserving the established physical direction across the ±180 representation boundary rather than issuing a blind endpoint sweep. Apply the same rule to explicit arithmetic rotation requests such as `R = current - 180`: calculate the unwrapped physical target, but command an equivalent controller-range representation when the result falls outside ±180° (for example, physical `-202.5°` is represented as `+157.5°`). Use bounded monotonic waypoints on both sides of the boundary (for example, `-142.5 → +177.5 → +157.5`) so the controller continues in the requested physical direction; do not send an out-of-range endpoint or let normalization reverse the intended sweep. After each leg, independently read the pose and inspect a fresh broad frame for people, collision, displaced objects, and cable/tubing tension before continuing. In the result, report both the unwrapped physical target and the final controller representation so equivalence is explicit. For a later absolute-R request that returns to the original orientation, use motion provenance rather than numeric endpoint subtraction: reverse the immediately preceding monitored physical sweep to unwind cable/tubing, especially when the represented endpoints differ by exactly 180° and shortest-path direction is ambiguous. Preserve fresh X/Y/Z, use bounded R-only reverse waypoints, and repeat independent pose plus broad-camera checks after each leg; reaching the same numeric orientation by continuing in the previous physical direction is not equivalent from a cable-wrap perspective. Re-evaluate the sign for each annotation—an upper-left adjacent target can require the opposite R direction from an upper-right target. After a controller power cycle, hold the freshly measured Cartesian pose rather than silently substituting nominal calibration coordinates. Treat any manual USB reseat, cable-slack adjustment, or camera/bracket handling as a new visual-calibration epoch: discard old centroids and pixel-per-degree estimates for steering, capture a fresh frame, and derive any new correction only from post-intervention frames. Verify every resulting pose and fresh frame, account for `safe_move` lifting and descending rather than twisting in place, and report any residual 2D centroid error honestly because one R degree of freedom cannot generally eliminate two image-axis errors. If the wrist camera hot-unplugs/re-enumerates during rotation, wait for its stable by-id node and capture a new verified frame; never continue from stale imagery, and stop further rotation if disconnects repeat. Also treat repeated FFmpeg “no packets/no image written” results as camera-feedback loss even when `/dev/video0` and the by-id link still exist: make at most one bounded capture retry, then stop motion at the independently verified probe pose and request a cable check rather than resetting USB or continuing blind. For a large fully visible circular cap, do not call it centered from a visual estimate or brightness-weighted color centroid alone: glare can bias that centroid. Use the full outline/ring geometry, report its horizontal bounds and midpoint against the frame center, and continue bounded sub-degree corrections until the measured residual reaches the pixel-quantization floor. If the operator changes illumination without touching the camera/bracket, treat it as a **photometric** recalibration rather than an extrinsic reset: preserve the verified R as a prior, capture a fresh stabilized frame, compare several reasonable color masks, steer from the threshold-stable outline midpoint, and stop instead of chasing differences within the 0–1 px quantization/noise floor. If the operator explicitly requests a full-range repeated-cap census, treat it as a distinct monitored scan: sample the full interval uniformly and discover candidates de novo; do not use prior cap centers as candidate angles or refinement seeds when the rotor may have moved. Require fresh full-outline evidence and controller pose for every cap, include wraparound spacing validation, persist one-row-per-cap provenance, and finish at the requested boundary with independent verification. Number caps by the current run’s explicit convention—normally increasing accepted R—and resolve later requests such as “move to cap 2” from the latest completed scan report, not from an older cap table or presumed persistent physical identity. When converting a camera-centered cap into a tool pose, rotate the calibrated camera-to-tool offset by `R − R_ref`; after that transformed move, do not require the wrist image to remain cap-centered because the camera was intentionally displaced. For any transformed cap target at low Z, split the motion into two externally observable stages: stop at transformed X/Y/R at a safe inspection Z, independently verify and inspect the local destination, then run a separately validated vertical descent. A `safe_move` that internally lifts and immediately descends is not a substitute for this inspection gate, especially in a sequence from one cap to the next. Before a transformed-cap pick, inspect the **deployed implementation**, not only `puda machine commands` prose: an observed M1Pro `pick_from` summary promised a 30 mm lift while the implementation performed no post-close lift. Likewise, `safe_move` to a higher endpoint can still route through configured safe height and descend to the requested Z. Preserve gripper-close and lift as separate protocol steps, disclose any safe-height overshoot, and verify physical retention from fresh imagery showing both a held tube and a vacated source slot whenever visible. See [references/dobot-m1pro-wrist-visual-servo.md](references/dobot-m1pro-wrist-visual-servo.md) and [references/dobot-orange-cap-wrist-scan.md](references/dobot-orange-cap-wrist-scan.md). For fresh black-empty-holder-ring censuses, de novo candidate interpolation/refinement, camera retry at a stationary verified pose, transformed holder XY, **exact-radius normalization that preserves the calibrated vector phase**, mat-fox's **90° clockwise plot convention** (`Y` horizontal, inverted vertical `X`), and exact native SpeedFactor on only the final placement descent, follow [references/dobot-m1pro-centrifuge-empty-ring-scan-and-speed-controlled-place.md](references/dobot-m1pro-centrifuge-empty-ring-scan-and-speed-controlled-place.md). For repeated MTP-to-centrifuge batches with an exact operator-specified final `Z`/`R`, a partially established occupancy boundary, native final-descent SpeedFactor, and waived fine visual checks, follow [references/dobot-batch-transfer-operator-final-z-and-waived-visuals.md](references/dobot-batch-transfer-operator-final-z-and-waived-visuals.md). If a scanned rotor tube is transferred to UUID-registered deck wells, treat labware coordinates as geometry rather than occupancy evidence and use a three-boundary sequence for every tube: source stage; pick/lift/destination stage; place/retreat. Verify one additional source vacancy after each pick and one additional upright destination tube after each place, then reconcile final count conservation. When the exact well is occluded, proceed without a new operator confirmation only if the current-operation ledger proves a directly verified outbound transfer from that exact UUID-backed well with no intervening refill/manual access/ambiguous run, and the operator explicitly requested that destination; otherwise pause. Preserve final occupancy as visually confirmed versus coordinate/ledger-supported. See [references/dobot-orange-cap-wrist-scan.md](references/dobot-orange-cap-wrist-scan.md).

Interpret an operator waiver of **visual pick/place verification narrowly**. It may authorize skipping detailed wrist-camera alignment, source-retention, destination-occupancy, or seating confirmation and proceeding directly from approved calibrated coordinates, but it does **not** waive fresh broad overhead checks for people, swept-path obstructions, collisions, displaced equipment, or dropped/loose labware. Preserve controller verification before and after motion. After the transfer, compare a fresh broad overhead frame with the preflight frame without turning that comparison into a forbidden precision check. If a newly loose, horizontal, or diagonally displaced tube is visible, stop all further robot motion, keep the robot at a verified safe retreat pose, and report the layers separately: the protocol/controller commands may have succeeded while the requested physical placement failed or remains unconfirmed. Do not attempt an automatic re-pick, reseat, or recovery move from the commanded history alone; require physical-state reconciliation and fresh operator authorization. If the broad camera is unavailable after such an anomaly, require explicit operator confirmation that the loose item was cleared, the path is clear, and the named destination is empty; scope that confirmation to one transfer rather than carrying it across later motions. Without visual, sensor, or operator outcome confirmation, describe pickup and seating only as **software-inferred**. See [references/dobot-direct-transfer-waived-visual-verification.md](references/dobot-direct-transfer-waived-visual-verification.md) for the direct six-step sequence, unavailable-camera gate, and evidence/reporting checklist. For deterministic multi-angle camera-to-tool geometry, run [scripts/rotate_camera_tool_offset.py](scripts/rotate_camera_tool_offset.py) rather than chaining offsets from the current transformed pose.
10. For relative Dobot XY moves, explicitly distinguish robot/base-frame deltas from tool-local deltas rotated by R, and distinguish per-axis distances from a total diagonal distance. Calculate from a fresh measured pose, preserve full target precision, and independently verify the result. Treat a request such as “move 50 mm in X” as an endpoint request unless the operator explicitly constrains the path. The deployed `safe_move` can satisfy the endpoint while rising to safe Z, translating, and descending; disclose that path before low-Z execution. If the operator requires X/Y-only motion at constant Z and no direct primitive is exposed, do not silently substitute `safe_move`—ask for approval of the safe-height excursion or add/test a narrow edge-mediated primitive. A prior explicit arm-orientation selection is not proof that a later `safe_move` preserved that branch: inspect raw `SetArmOrientation(...)` evidence or fresh joint angles before reporting the active branch. When the operator says **“use this transformation”** and replies to a previously established start/end pair, preserve that complete calibrated vector and rotate it by `Rcurrent − Rreference`; do not silently substitute a pure vector along the current R axis. A calibrated “30 mm” transform may have a measured magnitude and cross-axis component that differ slightly from nominal. If “use this transformation” conflicts with an explicit demand for **exactly** 30 mm and prior context has not resolved the convention, calculate both candidate endpoints and ask before motion. When the operator instead asks to make an existing set of transformed XYs an exact radius from a shared center, radially normalize each center-relative vector while preserving its direction, verify every resulting norm, and provide an equal-aspect labeled plot when requested. Treat those recalculated coordinates as analysis—not a new active calibration or motion target—until explicitly authorized. Once the operator confirms the calibrated convention, reuse it consistently. If an observed displacement differs from the nominal distance, report the actual magnitude and direction rather than forcing the nominal label. Near occupied labware, treat transform correctness and clearance as separate proofs: stage at the transformed X/Y/R at a supported inspection Z, inspect locally, and gate each lower-Z descent independently. See [references/dobot-m1pro-relative-coordinate-transforms.md](references/dobot-m1pro-relative-coordinate-transforms.md).

**Dobot Z-only and small vertical requests:** distinguish an endpoint request (for example, “move to `Z=27`”) from a path-constrained relative request (for example, “raise by 10 mm” or “move only Z”). The deployed `safe_move` is not a direct vertical primitive: even with unchanged X/Y/R and a target only a few millimetres away, it can lift to configured safe Z, emit a same-height target, and descend. Do not silently describe this as a small direct vertical move. Read a fresh pose first and preserve its measured X/Y/R. The current IMRE M1Pro edge exposes `move_vertical_to(z, speed_factor=0.25, blocking=True)`, which performs one direct controller-verified move to absolute robot-frame Z while preserving freshly measured X/Y/R; use it for approved direct absolute-Z paths and verify the final pose independently. If that command is absent from a future live registry, disclose the safe-height round trip and obtain approval before `safe_move`, or add a narrowly tested edge-mediated vertical primitive when operationally justified. For endpoint-only requests, `safe_move` may be used, but audit and report the actual path. Recompute relative targets from a fresh post-reconnect pose because restart or power-cycle state may differ materially from the last verified endpoint. For implementation/deployment, staged low-Z clearance, final-leg speed-factor scoping, and evidence requirements, follow [references/dobot-m1pro-direct-vertical-motion.md](references/dobot-m1pro-direct-vertical-motion.md). For the reusable motion-only named-well/overridden-Z procedure, absolute-versus-relative wording, scoped visual waiver, and audit checklist, follow [references/dobot-m1pro-motion-only-position-probes.md](references/dobot-m1pro-motion-only-position-probes.md).

11. For low-clearance moves near a rim, cap, vessel, rack, holder, or occupied centrifuge, use fresh overhead and wrist views. A monocular wrist image cannot prove the requested clearance. If X/Y also changes and the destination is not visible from the source, first stage at the requested X/Y/R at a supported safe inspection height, independently verify it, and capture local frames directly above the destination; this staging move is not task completion. When an object remains in the descent corridor, pause for operator confirmation or a revised target. If the operator revises the height while confirming clearance, discard the superseded target, preserve the other fresh measured axes, validate the revised pose, and execute only that revision. If the wrist camera is explicitly known disconnected and the operator waives its check, scope the waiver to fine/local visual evidence: retain fresh broad overhead people/path checks, use the active UUID-backed labware X/Y/R plus the exact operator-supplied Z override, stage and verify above the destination when feasible, perform no unrelated gripper actuation, and independently query the final controller pose. State that broad overhead imagery cannot prove fine well alignment. Also audit the deployed motion primitive before describing the second leg as a direct descent: this M1Pro's `safe_move` always uses `travel_z = max(safe_height, current.z, target.z)`, so a call from a verified stage such as Z=100 to Z=30 first rises to safe Z=240 and then descends; disclose that actual path rather than implying a simple 70 mm vertical move. See [references/low-clearance-vertical-moves.md](references/low-clearance-vertical-moves.md).
12. When an operator defines and labels a reusable physical pose, verify the measured pose independently before saving it. Persist a UUID-backed calibration artifact with machine/frame scope, requested versus measured pose, protocol/run linkage, and hash-linked camera evidence; then link it from `project.md`. Treat operator labels such as “center” as process landmarks rather than independent metrology claims. See [references/dobot-m1pro-named-position-calibration.md](references/dobot-m1pro-named-position-calibration.md). For operator-supplied CSVs containing many named deck positions—or revisions that rebuild a rectangular grid from approved opposite-corner probes—preserve source/backup provenance, distinguish grid wells from special positions, verify endpoint recovery and uniform pitches mechanically, and mark calculated/interpolated coordinates separately from individually controller-measured poses; follow [references/dobot-m1pro-tabular-labware-registration.md](references/dobot-m1pro-tabular-labware-registration.md). That reference also governs same-UUID CSV/JSON disagreement: never silently prefer JSON merely because it is structured, never average coordinates, and never reuse a pre-revision named-well protocol. Resolve the active geometry from explicit project history, revision provenance, timestamps/backups, and the approved calibration workflow; re-read that exact artifact immediately before authoring motion, record which artifact supplied X/Y/R, and preserve an operator-supplied Z override separately. Stop for operator clarification when precedence remains ambiguous.

### PipQuBot bare-pipette named-well position checks

When the operator asks to move the PipQuBot pipette to a deck well **without attaching a tip**:

1. Use the exposed `move_to_well(deck_slot=..., well_name=...)`; do not substitute `aspirate_from`, `dispense_to`, or `attach_tip`, and do not home unless explicitly requested. A home can unnecessarily reset Sartorius software state.
2. Confirm the active PUDA deck already maps the requested slot to the intended labware. Prefer a one-command protocol containing only `move_to_well`; avoid reloading or mutating deck state when the required mapping is already present.
3. Require fresh idle/no-run state, healthy edge, zero pending and ack-pending queue work, and a fresh enclosure image with no person/body part or obstruction. Compare the current endpoint against a known bare-nozzle reference when tip state is visually ambiguous; matching silhouettes are stronger evidence than judging one frame in isolation.
4. Audit the safe transit from edge logs: safe-Z lift, lateral X/Y move, final descent, and the driver's completed-position marker. Verify that no home, tip, or liquid-handling command occurred.
5. After movement, require fresh idle/no-run state, empty queue, unchanged edge restart count, and a post-move image showing the gantry over the intended labware area without collision. Individual well identity may be visually unresolved; establish it from the active calibration and emitted X/Y/Z.
6. If an independent `get_position` query is unavailable or affected by an async-dispatch defect, do not launch it merely for ceremony. Report coordinates as **driver-reported completion evidence**, not independently measured pose, and retain the command log plus camera evidence.

See [references/pipqubot-no-tip-position-checks.md](references/pipqubot-no-tip-position-checks.md) for the full physical/software deck-reconciliation decision, exact protocol-reuse rules, verification checklist, and session-specific calibration examples.

## Multi-machine workflow authoring

For workflows that hand labware between machines, treat station names as machine-scoped: robot-rack `A1`, process-station `A1`, and another machine's `A1` can have different coordinates and parameter schemas. Resolve each `(machine_id, station)` from existing validated protocols and command references, then sequence physical dependencies with distinct step numbers. **Before authoring a new protocol, query each live machine registry with `puda machine commands <machine-id>` and copy the exact exposed command names. Static `puda protocol validate` may accept a syntactically valid but unexposed command; live registry confirmation is required, especially when old protocol examples disagree.** For repeated workflows through a shared station, explicitly clear the processed item before advancing; otherwise the next placement can collide with an occupied station. When the protocol format is a static command list, generate the expanded sequence with a deterministic loop script and verify command count, step numbering, and per-position source/return mappings. Validation proves schema compatibility, not live command exposure, physical safety, or execution; after authoring, say **created and validated, not run** unless execution was separately authorized. See [references/multi-machine-protocol-design.md](references/multi-machine-protocol-design.md) for the general design and recovery checklist. For Dobot/capper decapping and recapping loops—including exact command names, one-time final homing, approval-gated tube return, and stop-boundary reconstruction—see [references/dobot-capper-loop-workflows.md](references/dobot-capper-loop-workflows.md). For image or inspection checkpoints, split motion into independently valid stages around the external capture/approval boundary, make capture failure prevent continuation, and follow [references/staged-camera-checkpoints.md](references/staged-camera-checkpoints.md). If the user asks whether a tube is capped, classify the captured pixels as **CAPPED**, **UNCAPPED**, or **UNCERTAIN**; never use a successful cap/decap command as visual evidence. Identify the requested rack or station and the exact corner or slot before classifying—do not silently analyze a nearby rack. Treat a dark rack well as **UNCERTAIN** unless tube occupancy and an open mouth are both visibly distinguishable. Choose the inspection location for visibility, not merely by station name: a fixed camera view of a tube in a rack may be blocked by the rack rim, so a robot pose “above A1” does not itself create a top-down camera view. When possible, inspect the tube at an unobstructed process station such as CAP before returning it to the rack; if the cap or open mouth is not clearly visible, report **UNCERTAIN** rather than using command success to break the tie. See [references/visual-cap-status-inspection.md](references/visual-cap-status-inspection.md) for target-localization, occupancy, classification, and reporting criteria. Use [scripts/capture_rtsp_frame.sh](scripts/capture_rtsp_frame.sh) to capture and validate a MediaMTX RTSP frame with retries before any approved continuation. Invoke it with `bash scripts/capture_rtsp_frame.sh OUTPUT.jpg [RTSP_URL]` because installed skill scripts may not retain the executable bit; do not assume direct execution will work. Resolve and pass the installation's configured stream URL explicitly when known: the script's fallback `/livestream` path is only a default, and a `404 Not Found` on that path does not prove camera loss when MediaMTX publishes the camera under another path such as `/ipcam`. Retry once with the authoritative configured URL, validate the resulting frame, and preserve the failed-path distinction in diagnostics.

When queue readiness must be verified and a local or containerized `nats` CLI is unavailable, use the NATS monitoring endpoint as a read-only fallback (normally `http://127.0.0.1:8222/jsz?consumers=true`). Parse `account_details[].stream_detail[].consumer_detail[]` and select the exact machine consumers, such as `cmd_queue_<machine-id>` and `cmd_immed_<machine-id>`; require `num_pending=0` and `num_ack_pending=0`. Treat `num_waiting=1` on the pull command consumer as an idle waiting worker, not queued work. Prefer a machine-scoped extraction over dumping the full monitoring response.

## Machine status snapshots

When asked for the status of one or several PUDA machines, report freshness and evidence layers instead of flattening everything to “healthy.” This applies even when `puda machine list` currently includes the machine: discovery plus a healthy container does not prove that an old controller socket still works.

1. Record the current host time, use `puda machine list` for discovery, then `puda machine state <id>` for each machine. Preserve and compare each state's timestamp with the check time; label an old retained value as **last reported idle/error**, not current controller state. When a read-only edge-mediated pose/status command is exposed, use it as the live controller-session check. If it fails with `Connection reset by peer` or `Broken pipe`, report the machine as **registered but controller-session degraded**, mark current pose unavailable, and do not present the last verified pose as current.
2. Inspect each edge container's running/health/restart status and the relevant NATS consumers. `num_waiting=1` with zero pending/ack-pending is an idle waiting consumer, not queued work.
3. Check recent edge telemetry/controller logs. A healthy container and live heartbeat can coexist with an unreachable device; for example, repeated `rr_status` `No route to host` errors make a capper **controller-unreachable/degraded** even when Docker health is green.
4. For Dobot, use only the existing edge-owned controller session; never open a second dashboard connection for a status probe.
5. Summarize per machine: current heartbeat, retained PUDA state plus timestamp, edge health/restarts, queue counters, and controller evidence. State explicitly when no motion or control command was issued.

## Controller-session rule

**Centrifuge websocket response-race pitfall:** On the deployed IMRE centrifuge edge, the background position publisher and a device command can concurrently read the same websocket. A lid-command acknowledgement may be consumed by the publisher and logged as `Position: Ok` or `Position: HomedN`; the command handler can then return `socket is already closed` or `Bad file descriptor` even though physical motion completed. Reconcile from the **raw semicolon-delimited position string in edge logs** plus a fresh overhead image—do not trust the public `get_position` value alone, because its `float(...)` fallback can collapse strings such as `0;50` to `0.0`. Never hard-code `50;0`/`50;50` as universal states: after both axes are homed, `0;0` is both-open and one normal device-2 close gives `0;50`. Do not retry a late-error close when the intended axis already reached `50`; the command is relative/non-idempotent and repetition can accumulate to abnormal values such as `150`. Global home is sequential; if logs prove only lid 1 reached `Homed1`, issue a fresh safety-gated device-2-only open rather than replaying global home. Preserve the failed PUDA run separately from the verified physical outcome. Follow [references/centrifuge-lid-command-reconciliation.md](references/centrifuge-lid-command-reconciliation.md) for the full procedure. A proper driver fix should serialize websocket request/response access or route replies through one reader.

When the edge is running, use the **existing edge path** for all status, recovery, and pose queries:

- Use published PUDA commands/protocols such as `get_pose`, when exposed.
- Do not open a second raw controller/dashboard TCP session merely to probe status. A separate session can compete with the edge's persistent controller connection and makes empty replies ambiguous.
- If an edge-mediated query does not return, report that the edge query itself failed; do not infer a physical pose.

### Stale edge-owned controller session recovery

A healthy edge container and fresh heartbeat can coexist with a stale controller socket. Treat `Connection reset by peer` or `Broken pipe` from an edge-mediated controller call as a controller-session failure, not as evidence that the requested motion ran.

1. Inspect edge logs to locate the exact failure boundary. If a motion command failed during its initial pose read, before any controller motion command such as `MovJ` was emitted, record that no motion was dispatched. Otherwise, treat the physical outcome as unknown and do not retry automatically.
2. Check PUDA state and queue/consumer counters. Require no active run, zero pending commands, and zero unacknowledged commands before restarting the edge.
3. Try the exposed PUDA reset path first when supported. If reset itself fails with a socket-level send error such as `Broken pipe`, do not keep retrying reset against the same dead session.
4. Restart only the affected edge to recreate its owned controller connection; never open a second direct dashboard connection as a probe. Before using Compose, recover the deployed project identity from `docker compose ls` or the container label `com.docker.compose.project`; the directory name may differ from the live project name. Invoke recreation with that explicit identity (for example, `docker compose -p <deployed-project> up -d --force-recreate <service>`). A plain `docker compose restart` can leave a long-running Python entry point alive when it traps interruption signals, and using the directory-derived default project can fail with a container-name conflict while the real project still owns the container. Verify that container uptime actually reset and startup logs are fresh before treating the session as recreated.
5. **Do not accept Docker `healthy` alone as successful reconnection.** Some edge health checks pass while the driver is still in its startup retry loop and has not initialized the controller or registered with NATS. Allow a bounded startup window through transient first-attempt outcomes such as a dashboard timeout or “closed the connection without replying”; do not declare failure or restart again while the driver is still retrying. Require all of: an explicit driver-initialized marker, `Edge Service Ready`, live appearance in `puda machine list`, a fresh PUDA state, empty command consumers, and a successful read-only edge-mediated pose/status query. The final query is what proves the recreated controller session actually works. Do not use an un-timestamped, interleaved, or startup-adjacent `GetPose` line from container logs as the current pose: Docker log ordering can mix buffered output around process recreation, and that value can disagree materially with a fresh post-ready query. Treat only the explicit post-ready edge-mediated query as the new pose source of truth.
6. If startup cannot open the controller socket, distinguish layers without competing with the edge-owned dashboard session: check route, ICMP/neighbor reachability, and edge logs. When the address is unreachable, report a network/controller-power problem. When it is reachable and returns a concrete reply, apply command- and installation-specific semantics rather than classifying solely from the numeric prefix. On this M1 Pro, the exact reply `-1,{},ClearError();` means no error remains and must be accepted **only for `ClearError()`**, followed by `EnableRobot()`; other nonzero command replies remain failures unless separately verified.
7. A genuine deterministic startup-command rejection will not normally be fixed by repeated container restarts. Preserve the raw reply, stop cycling the edge after one fresh-session confirmation, and ask the operator to check controller mode, safety/E-stop, and pendant alarms. Do not bypass the edge or ignore a rejected initialization step. This M1 Pro can retain a dashboard session after disconnect: after a controller power cycle, keep the edge stopped during boot, then start it as the first and only dashboard client. Do not run a direct preflight probe, even with the edge stopped, because it can consume the first responsive post-boot session and force another power cycle. See [references/dobot-m1pro-verified-motion.md](references/dobot-m1pro-verified-motion.md).
8. If startup never reaches NATS registration, treat old KV state and queue-consumer records as retained history; the machine is offline from PUDA even if the container says healthy. Do not dispatch `get_pose` until live registration returns.
9. Retry the requested motion only when logs proved the first attempt emitted no motion. After completion, run an independent edge-mediated pose query and recheck final PUDA state. After recreating a stale controller session, never assume the robot still reports the last pre-failure target: the fresh controller pose can differ from the last commanded or previously verified values because of real settling, controller reinitialization, or previously hidden measurement state. Use the post-reconnect pose as the new source of truth, and recompute any relative target from it; for an operator-supplied absolute target, execute that exact absolute pose rather than silently rebasing it.

This recovery pattern distinguishes a safely retryable pre-motion session failure from an uncertain interrupted motion.

### Read-only pose/joint query procedure

Before creating or running a pose or joint-query protocol:

**PipQuBot async-query pitfall:** A deployed edge may expose `get_position` as an async method while the queue dispatcher fails to await it. The signature still appears valid, but execution logs `Unable to serialize unknown type: <class 'coroutine'>` and `coroutine ... was never awaited`; no controller position is returned, the queue message is consumed, and PUDA can remain `idle` with a stale run ID because the client never receives a response/COMPLETE boundary. Treat this as a dispatcher failure rather than controller or physical-position evidence. Confirm queue `pending=0` and `ack_pending=0`, and confirm logs show no motion command. A CLI `reset` may clear the stale run ID before the machine rejects the unexposed `reset` method, leaving a retained `error` state. Do not keep retrying reset. After a fresh camera safety check and proof that no tip/liquid state must be preserved, restart only the affected edge, wait for startup home/Sartorius initialization and NATS registration to complete, then require fresh `idle`, `run_id=null`, and empty queue counters before any authorized workflow.

1. Identify the actual machine command with `puda machine commands <machine-id>`; user terminology may differ (for example, `get_position` may be exposed as `get_pose`).
2. Locate an existing PUDA project (`puda.config` and `project.md`) and run the protocol from that project root. Do this before authoring a temporary protocol: `puda protocol run` requires project context even for a read-only query.
3. Reuse a prior query protocol when one exists, then check `puda machine state <machine-id>` immediately before dispatch.
4. Inspect the project history for recent query timeouts. If the same edge-mediated query recently stalled, tell the user before launching a potentially long wait; do not imply that dispatch has occurred until `puda protocol run` has actually started.
5. Report the query response as the driver-reported pose only after it returns. If it times out, report the pose as unknown and follow the interrupted-run recovery procedure; do not retry automatically.

## Interrupted or slow runs

If a protocol invocation is interrupted, times out, or remains `busy`:

1. Assume its physical effect is **unknown**; never automatically resend the same motion. A timed-out/interrupted background wait or an ordinary chat message is not process cancellation—retain the process session ID and use an explicit kill/cancel only when the user requests stop.
2. Inspect the PUDA state and edge logs first.
3. Treat client interruption, queue pause, and physical cancellation as separate events:
   - Interrupting or killing `puda protocol run` may send `COMPLETE`, but an already accepted edge command can continue to physical completion afterward.
   - A queue-level `pause`/`resume` transition may succeed even when the machine's immediate method reply says `Unknown or restricted command`; re-read `puda machine state` and edge logs instead of trusting only the CLI exit code.
   - Determine the true stop boundary from per-command edge responses and motion logs, including responses that arrive after the client interruption timestamp. Never report the CLI's last printed command as the physical stop boundary without this check.
4. If it remains active/busy or leaves pending work, first check `puda machine commands <machine-id>` for an exposed reset/cancel/recovery command. Use `puda machine reset <machine-id>` only when that path is actually supported; do not guess that every edge exposes `reset`. After a syntactically valid but unexposed command is rejected, a stale PUDA `error` state may coexist with working read-only commands and a healthy controller. Reconstruct the completed boundary, verify the rejected command caused no physical action, correct the command from the live registry, and run only the reviewed uncompleted suffix; a fresh START can establish the new run state without inventing a reset operation.
5. Inspect queue/consumer state before restarting an edge. **Never purge or alter a motion queue while a physical run is active**; first stop or recover the run through a supported path. Only then remove stale motion messages before re-enabling consumption, and verify the queue has zero pending and zero unacknowledged messages.
6. Log the reset time and explicitly state that final robot/labware position is unverified unless independently confirmed.
7. For a partially completed pick/place protocol, reconstruct the last confirmed step before choosing recovery:
   - If the pick pose, close-gripper command, and subsequent command boundary are recorded but placement failed before opening, **do not rerun the pick automatically**; that can double-pick or crush labware.
   - Preserve the gripper output across edge recovery when the driver reset contract does not alter it, but treat actual labware retention as unverified without a gripper sensor, camera, or operator confirmation.
   - Resume only the placement step after checking measured pose, controller alarm/branch state, queue emptiness, and receiving authorization for the recovery motion.
   - Verify the destination pose and accepted open-gripper command separately; describe physical placement as sensor-confirmed, operator-confirmed, or software-inferred.

### Explicit M1Pro arm-orientation changes

When an operator requests a raw arm-orientation branch value such as `SetArmOrientation(1)`, keep the action edge-mediated. If the live registry does not expose it, add a narrowly validated public driver wrapper with RED→GREEN tests, redeploy under the existing Compose project identity, and verify the exact controller reply plus unchanged Cartesian pose. **Do not call this a physical arm-orientation change:** `SetArmOrientation` alone only selects the inverse-kinematics branch for subsequent Cartesian motion. To physically change the elbow posture at the same Cartesian home, issue the explicit orientation immediately followed by a reviewed slow home/move, after broad swept-path and empty-gripper checks; then verify the branch from before/after joint angles and imagery because Cartesian pose can remain identical. Record Cartesian home and branch as separate outcomes: a second `get_pose` proves the home endpoint, while fresh joint angles provide branch evidence. Installation-specific joint signatures belong in [references/dobot-m1pro-verified-motion.md](references/dobot-m1pro-verified-motion.md), not in generic assumptions. Treat any visible fingers or other body part intruding at the enclosure boundary as a hard stop and require a genuinely fresh clear frame. The setting is stateful but potentially ephemeral: deployed `safe_move` or `pick_and_place` logic may automatically select a branch from source/target Y and overwrite it on the next motion. For the full exposure, deployment, physical-change, and verification procedure, follow [references/dobot-m1pro-explicit-arm-orientation.md](references/dobot-m1pro-explicit-arm-orientation.md).

## Motion-validity versus completion diagnosis

A pose can pass the driver's generic workspace check yet still fail to complete physically. For a `safe_move`, identify the last segment emitted (typically rise → lateral travel at safe Z → final descent) and distinguish:

- **Validation rejection:** the driver returned an explicit workspace/parameter error before sending motion.
- **Controller rejection:** `MovJ`, orientation selection, or another command returned a nonzero controller status or set a controller alarm.
- **False completion:** `MovJ`/`Sync` appeared successful, but a measured post-motion pose remained outside tolerance.
- **Controller completion stall:** the driver logged the final `MovJ` but then waited for a blocking completion/synchronization reply without a result.
- **Physical outcome:** unknown unless a post-motion edge-mediated pose/state response succeeds.

On a false completion, preserve the requested target, measured pose, raw orientation/`MovJ`/`Sync` responses, controller mode, and error IDs before clearing the alarm. Decode the error ID from the model-appropriate official alarm table; do not infer the alarm meaning from the number alone. If the alarm reports a joint limit or inverse-kinematics failure, treat arm-orientation/kinematic branch selection as a concrete hypothesis and test only one reviewed branch change at a time.

For cross-side pick/place paths that require different kinematic branches, **do not switch to the destination branch while still at the low source pose**. The safe sequence is:

1. Select or restore the branch compatible with the measured current/source pose.
2. Lift vertically to safe height and verify that pose.
3. Switch to the destination-compatible branch at safe height.
4. Travel laterally, verify, then descend.

A failed attempt may leave the destination branch selected even though the robot never left the source pose; clearing the alarm or restarting the edge may not reset that branch. Recovery must therefore restore the source-compatible branch before the first lift.

Do not label a completion stall as a workspace-limit error without an explicit controller/driver rejection. Do not automatically retry an uncertain motion. Capture the exact final target and command-response gap in the run log.

### Gripper polarity and physical-state verification

Treat a named `open_gripper`/`close_gripper` method and an accepted digital-output reply as **command intent**, not proof of the physical jaw state. Digital-output polarity is installation-specific and may be active-low.

1. Establish the real mapping with a stationary, controlled open/close test and operator, sensor, or camera observation. Do not infer polarity from `0`/`1` conventions.
2. Encode the observed mapping in a regression test at the driver boundary (for example, expected `DOExecute(channel, state)` calls for open and close).
3. Verify pick/place sequencing separately: pick must produce a physically open jaw before grasp and a physically closed jaw after grasp; place must physically open at the destination.
4. If operator observation reveals reversed polarity, correct prior audit entries that claimed physical pick/release from accepted commands alone. Do not rerun the full transfer automatically; first deploy the polarity fix, command a stationary safe state, and ask for or obtain physical confirmation.
5. Without gripper feedback, report jaw/labware state as operator-confirmed or software-inferred. A successful output command only proves controller acceptance.

See [references/dobot-m1pro-verified-motion.md](references/dobot-m1pro-verified-motion.md) for a concrete 4-axis false-success signature, alarm-preserving diagnosis, cross-side recovery ordering, verified-motion hardening, and the observed M1 Pro gripper polarity.

## Network and DNS diagnosis

1. Read the edge configuration first. When a controller is configured with a numeric private IP, DNS/MagicDNS is not part of that controller connection path.
2. Verify route, ICMP reachability when permitted, and the relevant controller TCP ports from the host/edge network before blaming DNS.
3. Check Tailscale and system DNS separately. A Tailscale warning about an unreachable optional IPv6 resolver can coexist with working MagicDNS and does not explain a healthy direct IPv4 route to a numeric controller endpoint.
4. Do not disable accepted Tailscale DNS merely to suppress a warning; that can break working MagicDNS. Repair the real issue at the appropriate scope (for example, add IPv6 reachability or remove the unreachable resolver in tailnet DNS settings).

## Persisting an operator-defined robot home pose

When an operator asks to move to a Cartesian pose and save it as the new home, treat **physical positioning** and **persistent configuration** as two separately verified outcomes:

1. Resolve the requested frame and axes, perform the normal pre-motion safety checks, move through the existing edge, and independently read back the measured pose before calling the landmark verified.
2. Identify the actual runtime source of the home pose (environment/configuration, edge entry point, or driver constructor). Update that source and any operator-facing diagnostic/default-home script that intentionally mirrors it; do not rewrite historical protocols or calibration records merely because they contain the old home.
3. Before rebuilding from a dirty checkout, inspect every unrelated diff and compare affected local source hashes with the currently deployed container/image. Proceed only when existing dirty changes are known deployment fixes already present in the running image, or isolate/reconcile them so the rebuild cannot silently deploy unrelated work.
4. Run the repository's declared test mechanism plus syntax and Compose/config checks, then rebuild/recreate using the existing Compose project identity.
5. Verify the live container is healthy, ready on NATS, has empty command queues, and contains the new home value in the deployed runtime source/config. Use an edge-mediated `get_pose` to confirm controller connectivity and that restart did not disturb the endpoint.
6. Do **not** invoke `home` merely as a persistence test when home has side effects such as opening the gripper. Only execute a live home cycle after proving nothing is intentionally held and the full path/cable sweep is safe. Otherwise distinguish “new home configuration is deployed” from “a post-deployment home cycle was physically exercised.”
7. Record the move protocol/run and requested-versus-measured pose in project history. Save the durable home value in environment memory only after deployment verification.

## Fault clearing and enablement

Use the edge's documented reset/recovery command and verify both its response and the resulting PUDA/controller state. For controllers that restrict commands while in an error mode, recovery must begin with the one command allowed in that mode—commonly `ClearError()`—before attempting disable/enable operations. Interpret replies per the exact command and verified installation behavior: on the IMRE M1 Pro, `-1,{},ClearError();` is a successful no-error/cleared result, so continue to `EnableRobot()`; do not generalize this exception to `DisableRobot()`, motion commands, other nonzero codes, or other controllers. Allow a short documented settling interval after clearing when the controller transitions asynchronously; an immediate `DisableRobot()` can otherwise be rejected even though error clearing succeeded.

A robust recovery sequence is:

1. Query controller mode and error IDs through the existing edge when exposed.
2. Clear the controller error.
3. Wait the controller-specific settling interval and confirm the error mode has cleared when possible.
4. Disable and re-enable only if the driver requires that reset cycle.
5. Verify controller mode, error IDs, PUDA state, and a read-only pose through the edge.

Do not blindly ignore a rejected reset command. Preserve the raw response and distinguish an error-mode command restriction from a broken socket or stale controller session.

## Offline motion postmortems

When the robot is offline or the user prohibits controller contact/code changes, perform a read-only postmortem instead of attempting a live reproduction:

1. Correlate PUDA project history, run logs, and `command_log` rows.
2. Inspect edge logs without starting/restarting the edge.
3. Compare repository HEAD with the exact deployed container/image source; build time and checked-out Git history alone do not prove what ran.
4. Trace whether execution reached `MovJ`, then distinguish requested targets from edge-measured poses.
5. Test false-success behavior offline with a fake controller returning rejection or empty responses.
6. Check workspace validation separately from orientation/kinematic branch selection.
7. Verify Git remains unchanged before reporting.

Treat a recent orientation feature as a possible *trigger* for controller rejection, but distinguish it from the deeper error-handling defect that suppresses rejection or returns the target without physical verification. Do not claim orientation is causal unless raw controller responses or a controlled reproduction establish it.

See [references/offline-motion-postmortem.md](references/offline-motion-postmortem.md) for the detailed evidence order, failure signatures, and reporting checklist.
